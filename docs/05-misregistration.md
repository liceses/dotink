# ⑤ 套印不齐：多版成像规范

> **实现** [`press.js`](../press.js)（零依赖经典脚本，挂 `DotInk.press`）· **演示** [`press.html`](../press.html) ·
> **成片** [`tools/press-reel.html`](../tools/press-reel.html) + [`tools/press-reel.mjs`](../tools/press-reel.mjs) ·
> **管线** [`tools/press-clip.mjs`](../tools/press-clip.mjs)（任意视频 → 格子图集）+ `press-reel.mjs --clips` ·
> **自查** [`check/press.mjs`](../check/press.mjs)（26 条 / 633 条断言，含 1 条汇总自检；已接进 `npm run check`）。
>
> 本页是**套印层**的规范：一张画面怎么拆成 N 张版、版与版之间怎么"对不准"、以及怎么判定它没画坏。
> **单色层的判据（M1 / M2 / M3）在套印层不适用** —— 那不是它的口径，套上去只会得到恒假的门禁。
> 单色层的规范仍以 [`STANDARD.md`](../STANDARD.md) 为准。

---

## 1 · 是什么，不是什么

| 是 | 不是 |
|---|---|
| 一张画面拆成 **N 张版**，每张版仍然只有「有墨 / 没墨」 | 不是"给单色网点上色"—— 颜色不在版上，在**叠印**里 |
| 颜色 = 掩码查表（第 k 项 = 位掩码 k 的那几版叠在一起） | 不是逐像素调色、不是 alpha 混合、不是 RGB 直接画 |
| 版与版之间留**可控**的对不准 → 边缘露出单版色（漏色重影 / color fringe） | 不是抖动噪点、不是故障艺术、不是随机脏 |
| 偏移是 `t` 的**确定性函数**，同参数永远同一帧（可出视频、可随机 seek） | 不是 `Math.random()` 抖出来的"手抖感" |
| 1-bit 纪律的推广：判据从"有没有灰阶"变成"**有没有跑出套印格点集**" | 不是取消 1-bit，是把 1-bit 用到 N 张版上 |

一句话：**每版还是 1-bit，颜色是叠出来的，对不准是画出来的。**

## 2 · 与单色层的关系：press 是 render 的严格超集

旧的单色代码**不用改**。同场、同 `cell`、同 `maxFrac`、同 `areaMap`，只要满足下面四条，**单版 press 与 render 直画逐字节相同**：

| 条件 | 为什么 |
|---|---|
| 只给一版（`inks.length === 1`） | N=1 时 palette 只有纸与墨两项 |
| 这一版的 `angle === 0` | **点阵不旋转**，点正好落在格心，与 render 的网格通道是同一批点位 |
| `plates` 里那一版就是 render 用的那个场 | 同一份 `Float32Array` 或同一个函数 |
| render 侧也传 `shutter: 0` | press 内部**写死** `shutter: 0`（`press.js:653`）；render 默认是 `1/28` |

实测（逐字节比整帧；`.visual-audit/eq3.cjs`，两轮复现）：

| 参数 | 背板像素 | 差异像素 |
|---|---|---|
| `angle 0` · `cell 8` · `maxFrac .40` · `areaMap true` · `scale 1.5` | 2 073 600 | **0** |
| `angle 0` · `cell 12` · `maxFrac .48` · `areaMap true` · `scale 1` | 921 600 | **0** |
| `angle 0` · `cell 8` · `maxFrac .40` · `areaMap false` · `scale 1.5` | 2 073 600 | **0** |
| `angle 45` · `cell 8` · `maxFrac .40` · `areaMap true` · `scale 1` | 921 600 | **315 723（34.26%）** |

> ⚠ **`angle 45` 不等价**，别把"单版"当成"哪一版都行"。45° 会把点阵整体转过去，点位一挪就不是同一个网格通道了。
> 旧版本页写的是 18.22% / 377 819 px —— 那是**按通道数**算的；按**像素**算是 **34–35%**（随场变）。报数请写清口径。

> ⚠ **不要从全局借 `_mulberry32`**。`press.js:26-33` 记的是一次真实的静默失效：早期版本借 `DotInk._mulberry32`，
> 兜底写成 `|| (() => () => 0.5)`，缺 `fields.js` 时四版相位退化成同一个常数 → **整组一起平移**，
> 套印偏差实际为 0，而 `regPx` 仍不为 0（它量的是绝对位移）—— 看起来"有偏移"，其实版间零相对错位。
> 现在 `press.js` **自带一份私有实现**（与 `fields.js` 的 mulberry32 逐位相同），所以**装载顺序不影响结果**。

顺带一个反直觉的实测：`scale 1.5` / `cell 8` / 干涉场下，render 单色 **`shutter 1/28` = 20.3 ms**、**`shutter 0` = 13.4 ms**、
press **四版 = 12.3–14.4 ms**（§8 同一台机器）。运动模糊要画两帧，四张版反而更便宜 —— 所以"多版一定更慢"是错觉，
慢的是分色（§5）与读回（§8）。

## 3 · 色彩上限：2^N 是**上限**，不是色数

减色叠印是**乘法**（`press.js:98`：透过率 `rgb / paper` 逐通道相乘），所以两个不同的掩码可能算出**同一个 RGB**。
四版 `CLASSIC` 实测：16 个掩码，**实到 15 色**，碰撞一对 —— code 7（CMY）与 code 15（CMYK）都是纯黑 `(0,0,0)`。

| 版组 | 版数 N | `paletteSize` = 2^N | `paletteColors`（实到） | 碰撞对数 |
|---|---|---|---|---|
| CMY | 3 | 8 | **8** | 0 |
| CMYK（`CLASSIC`） | 4 | 16 | **15** | 1（`[[7,15]]`） |
| CMYK + 橙 O | 5 | 32 | **20** | 12 |
| Hexachrome（CMYK + O + G） | 6 | 64 | **35** | 29 |
| Hexachrome + 蓝 + 红 | 8 | 256 | **85** | 171 |

同一套 `CLASSIC` 四色**再往后挂灰阶**（[200,200,200] / [150,…] / [100,…] / [50,…]），1→8 版实到：
`2 / 4 / 8 / 15 / 29 / 57 / 109 / 173` 色，碰撞对数 `0 / 0 / 0 / 1 / 3 / 7 / 19 / 83`。
六色前缀 1→6 版是 `2 / 4 / 8 / 15 / 20 / 35` 色。

> ⚠ **碰撞不是普遍规律，是几何后果**：CMY 三版 8 掩码正好 8 色，一个都不撞；
> 撞的是"黑版压在 CMY 满版上"这一处（所有 `CMYK` 子集里 code 7 与 15 都同色）。
> 版数上限 **8**（`press.js:89` 抛错：`2^8 = 256` 已经够多，再多 palette 反而不受控）。

### 3.1 四个色数字段，别混

`measure()` 一次给四个数，关系是 `colors ≤ codes ≤ paletteSize` 且 `colors ≤ paletteColors ≤ paletteSize`：

| 字段 | 含义 | 源 A 对齐 | 源 A + `amp 2` |
|---|---|---|---|
| `paletteSize` | `1 << N`，**理论上限** | 16 | 16 |
| `paletteColors` | 格点集里**真实有几个颜色**（`distinctColors`，已折叠碰撞） | 15 | 15 |
| `codes` | **这一帧**用到过几个掩码 | 8 | **16** |
| `colors` | **这一帧**画布上真出现过几个 RGB（按颜色折叠，不是按掩码） | 7 | 15 |

右两列是同一张源 A（§9 那张）的实测。`colors < codes` 就是碰撞在这一帧里真的发生了；
用 `codes` 冒充色数会把碰撞藏起来（`press.js:808-810` 的注释说的就是这件事）。

### 3.2 四版调色板（`CLASSIC`，纸 `#F2F3F2`）

| code | 掩码 | RGB | 读起来是 |
|---|---|---|---|
| 0 | — | 242,243,242 | 纸 |
| 1 | C | 0,174,239 | 青 |
| 2 | M | 236,0,140 | 品红 |
| 3 | C+M | 0,0,138 | 蓝 |
| 4 | Y | 242,241,0 | 黄 |
| 5 | C+Y | 0,173,0 | 绿 |
| 6 | M+Y | 236,0,0 | 红 |
| 7 | C+M+Y | **0,0,0** | 黑（撞） |
| 8 | K | 12,13,14 | 黑 |
| 9–14 | 含 K 的双版 / 三版 | 0,9,14 / 12,0,8 / 0,0,8 / 12,13,0 / 0,9,0 / 12,0,0 | 近黑（黑版压暗） |
| 15 | C+M+Y+K | **0,0,0** | 黑（撞 7 号） |

> ⚠ 9–14 这几项**几乎是黑的**：减色乘法下"黑版再叠一两个色版"只会更暗。四版套印的有效色域比"15 色"听起来窄得多 ——
> 观感上的彩色全部来自 1–6 号（单版与双版）。这也是为什么**版一错位，画面立刻"变彩"**：单版孤岛的面积涨了。

### 3.3 六色为什么值：色域与代价

六版（Hexachrome：CMYK + 橙 `[255,108,0]` + 绿 `[0,166,81]`）把调色板从 15 色抬到 **35 色**（64 掩码，29 对碰撞）。
但**色数不等于调子准**：十色靶实测（口径见 §5.1）四色玫瑰斑平均色差 28.8，六色玫瑰斑 **27.3** —— 只赢 1.5；
同角度下六色反而更差（64.2 vs 43.2）。六色真正的价值在**饱和色域**（橙 27.0 / 绿 23.7 / 肤 28.9 / 墨绿 35.4），
不在"多出 20 个颜色"这件事本身。

## 4 · 两个网角体裁

### 4.1 准同角度（默认，套印体裁）

四版同角（45°）或极接近（0/2/4/6°），**靠 drift 把它们晃开**。对齐时四版圆点同心、颜色干净；一晃开，边缘一圈露出单版色 —— 那正是"早期印刷机没套准"的样子。

- **用**：四色、绝大多数情况。这是本层的默认体裁（`press.html` 的 `SAME` 就是四版全 45°）。
- **成立条件**：`cell ≥ 8`、`maxFrac ≤ .45`。点太满或格太小，四版圆盘本来就挤在一起，偏移只能挤在半个格里，读起来是"边缘毛"而不是"漏色"。
- **失败模式**：`regPx` 超过约 **1 个格**（`amp ≳ cell`）后四版圆盘几乎不再重叠，画面退化成**满屏斜纹**（§12）。
- **六色要小心**：六版同心时色数会**塌回 15**（`codes` 21 / 2^6 = 64），一错位就炸到 `fringe .4536`（§4.3 表）。

### 4.2 玫瑰斑（可选体裁，四色 15/75/0/45）

标准印刷网角。四版点位本来就不同，叠出来是**玫瑰斑**（rosette）。

- **用**：想让"印刷品本身的花纹"当主角时；做静态对照图；**六色（Hexachrome）** 时它是默认（理由见 §4.3）。
- **失败模式：彩纸屑**。四版点位互相错开 + 覆盖率一高，每一格都变成三四个不同颜色的小点，读起来是撒了一把彩色纸屑 —— **图像内容被吃掉**。
  实测（源 A / `cell 8` / `maxFrac .40`）：玫瑰斑即使 drift 完全关掉，`fringe` 也有 **0.3069**（同角度对齐只有 **0.0623**）。
- **另一条**：玫瑰斑对 drift **几乎不敏感** —— `amp` 0→5，`fringe` 0.3069 → **0.2908**，`platesPerInk` 1.310 → **1.333**。它天生就"错"着，你再晃它也晃不动。

> ⚠ **别把玫瑰斑当默认**（四色）。它是印刷厂的取舍（牺牲单张清晰度换大批量不撞摩尔纹），不是"更专业"。
> 四色层的表达力在"几乎对齐又不断错开"，那只有准同角度给得了。

### 4.3 六色：体裁的选择反过来了

六版时两个体裁的实测（源 A / `maxFrac .40` / 覆盖域分色 sweeps 24 / `tacLimit 4.2`）：

| 体裁 | 状态 | `regPx` | `fringe` | `platesPerInk` | `colors` / `codes` | `tac` | `inkCov` |
|---|---|---|---|---|---|---|---|
| 玫瑰斑 | 对齐 | 0 | **0.3584** | 1.600 | **35 / 64** | 1.0403 | 0.6502 |
| 玫瑰斑 | `amp 5` | 4.15 px | 0.3556 | 1.607 | 35 / 64 | 1.0407 | 0.6475 |
| 准同角度 | 对齐 | 0 | 0.0643 | 2.998 | **15 / 21** | 1.0421 | 0.3476 |
| 准同角度 | `amp 5` | 4.15 px | **0.4536** | 1.481 | 28 / 45 | 1.0382 | 0.7009 |

读法：玫瑰斑**对齐时就已经满色**（35 色、64 掩码全用上），drift 加不加几乎一样；
准同角度对齐时六版同心、颜色互相吃掉只剩 15 色，一错位立刻炸成 0.4536 的漏色率。
所以六色的默认体裁是**玫瑰斑**（`tools/press-reel.html` 默认 `angles=rose`），四色才是准同角度。

## 5 · 分色：从 RGB 到 N 张版

### 5.1 三条路，实测色差

| 函数 | 在哪解 | 四色 | 六色 | 成本（160×90 格） |
|---|---|---|---|---|
| `separate(rgba,w,h,cols,rows,{ucr})` | UCR 公式，闭式 | 可用 | **只会拆 CMYK** | **15.3 ms** |
| `separateN(inks,…)` | 密度域 NNLS（log 空间） | 可用 | **解不出 O/G**（mean 0） | 54.7 ms |
| `separateCov(inks,…,{curve,srcAvg,sweeps})` | **覆盖域** | 可用 | **35 色** | 24.5 / 41.7 / 50.8 ms（sweeps 12/24/30） |

十色靶色差实测（`.visual-audit/probe-eval.js`；**口径**：`cell 7` / 30×30 格 / 210×210 CSS / `scale 1` /
`maxFrac 1/√2` / sweeps 24 / `free` / `tacLimit 0` / 跳过最外 2 圈；误差 = 渲染画布按格均色 vs `cellAverages×255` 的 sRGB 欧氏距离）：

| 配置 | 平均 | 最差 | 最差色 |
|---|---|---|---|
| 四色 · 玫瑰斑 · 覆盖域 | **28.8** | 39.5 | 墨绿 |
| 六色 · 玫瑰斑 · 覆盖域 | **27.3** | 40.9 | 中灰 |
| 四色 · 准同角度 · 覆盖域 | 43.2 | 73.8 | 墨绿 |
| 六色 · 准同角度 · 覆盖域 | 64.2 | 130.9 | 近黑 |
| 四色 · 玫瑰斑 · NNLS | 44.9 | 88.9 | 绿 |
| 六色 · 玫瑰斑 · NNLS | 44.9（与四色逐项相同 —— O/G 解出 0） | 88.9 | 绿 |
| 四色 · 玫瑰斑 · 公式 | 84.5 | 136.8 | 紫 |
| 六色 · 玫瑰斑 · 公式 | 84.5（与四色相同 —— 公式只认 CMYK） | 136.8 | 紫 |

> ⚠ **跨 `scale` 不可比**：同一批靶，四色玫瑰斑 `scale 1` 28.8 / `scale 1.5` 20.2 / `scale 2` 16.6
> （满墨覆盖率 0.9763 / 0.9884 / 0.9945）。每格设备像素越多，格内平均越接近目标。引用时必须带 `scale`。

### 5.2 覆盖域分色 `separateCov`

这个引擎按**覆盖率**记账（一格上这版盖了多少面积，合成是 `(1−c) + c·t`），所以分色也要在覆盖率域解：

```
R_c = Π_i (1 − c_i·d_ic)      d_ic = 1 − t_ic（这版在该通道最多能压掉多少）
```

求解是**逐版闭式坐标下降**（一维二次 + ridge 1e-3 + 投影到 `[0, maxCov]`），不需要梯度、不需要雅可比。
`mode:'base'` 多一层：先让 CMYK 背调子，O/G 只吃残差（3 个方程撑 6 个未知数，不加约束会把暗部均摊成彩色纸屑）。

**它依赖一条必须先量出来的曲线**：`coverageCurve(opts)` —— 墨量 `w` → 这一版真盖住了多少格面积。
因为 `r = rMax·√w` 只在圆盘互不相交时给出线性关系，`maxFrac` 一大，并集覆盖率就被几何压住。实测：

| `maxFrac` / `cell` / `scale` | `maxCov` | `w .5` → 覆盖 |
|---|---|---|
| .40 / 8 / 1.5 | **0.4792** | 0.2569 |
| 1/√2 / 7 / 1 | **0.9763** | 0.7351 |

> ⚠ `coverageCurve` 是**实测**不是解析式（引擎是逐像素栅格化 + 抗锯齿，解析圆盘在小 `w` 处差 14%），
> 一次约 **18–24 ms**。**必须缓存**：只在 `cell` / `maxFrac` / `scale` / `areaMap` 变化时重建（`press.html` 与 `press-reel.html` 都这么做）。

### 5.3 `separateN` 不能当六色分色用

密度域 NNLS 在四色下比公式好（44.9 vs 84.5），但六版时**解不出 O/G**：`O` mean 0 / max 0.0001、`G` 同，
C/M/Y/K 与四版**逐项相同**，`reconstructError` 六版 1.8054 vs 四版 1.8064（几乎没变）。
原因是它解的是密度 `t^a`，而这个引擎按覆盖率记账 —— 记账口径错位，六版就退化成四版。

## 6 · 套印偏移的模型

偏移**不是**随机抖动，是 `t` 的纯函数（`press.js:134-150`）：

```
每版相位：  a = mulberry32(seed·7919 + i·131)()      b = mulberry32(seed·104729 + i·37)()
            dx = amp·(0.45 + 0.55·b)·sin(speed·t + 2πa)
            dy = amp·(0.45 + 0.55·a)·sin(speed·0.77·t + 2πb)
微转（可选）：ph = mulberry32(seed·3163 + i·17)()    dθ = rot·sin(speed·0.6·t + 2πph)
```

- **每版的相位由 `(seed, i)` 决定**，四版两两不同（`amp 5 / seed 3 / t 0.9` 实测：C 3.00 px / M 2.84 / Y 2.44 / K 3.58）。
- 两个**不同频率**的正弦叠加（`speed` 与 `0.77·speed`），所以轨迹是李萨如式的、不会很快重复。
- 全程**没有 `Math.random()`**：同 `(seed, amp, speed, rot, t)` 永远同一帧 —— 这是能出视频、能逐帧复现、能随机 seek 的前提。

| 参数 | 语义 | 建议区间 | 实测 / 备注 |
|---|---|---|---|
| `amp` | 位移**幅度**（CSS px） | **2–7** | `regPx` 峰值 **0.705–1.238·amp**（6 seed × 4 版 × 601 点） |
| `speed` | 角频率（rad/s） | **0.5–1.0** | 主周期 `2π/speed` ≈ **6–13 s**；`0.77` 分量周期更长，所以不会整齐地来回 |
| `rot` | 微转**幅度**（度） | **0.2–0.5** | `regRot` 均值 **0.887·rot**、峰值 **1.000·rot** |
| `seed` | 换相位（也轻微换幅度） | 任意整数 | 换 seed 只换"什么时候歪到哪"，不换体裁 |

`drift` 也可以直接给函数：`(name, t, i) => [dx, dy]`（`press.js:135`）—— 要跟音乐对拍、或要一次性扫过某个偏移序列时用它。

> ⚠ **`amp` 不是"峰值位移"**。峰值在 0.705–1.238·amp 之间，随 seed 浮动。要卡死上限就自己 clamp `amp`，别指望 `regPx ≤ amp`。

> ⚠ **`rot` 比位移"更有效"，而且它不产生平移**：实测 `rot .5`（`amp 0`，`regPx` 恒 0）就能把 `fringe` 从 0.0623 拉到 **0.1454**，
> 比 `amp 5`（3.58 px 位移，0.2804）温和得多。想要克制的"没套准"，优先给 0.5–1.5 px 位移 + 0.1–0.2° 微转，而不是一味加 `amp`。

## 7 · 判据

套印层有**四条硬判据**（`press.html` 的判据表就是这四条），外加**两个只能同角度基准用的观察量**。

### 7.1 四条硬判据

| # | 判据 | 量 | 门限 | 为什么 | 状态 |
|---|---|---|---|---|---|
| 1 | **只落在套印格点集上** | `badPixels` | **=== 0** | 颜色是查表来的，画布上每个像素必须精确等于 `palette[code]`。这条是真 `getImageData` 读回逐像素比对（`press.js:835-842`），**不是同义反复** | 实测固化：往画布上涂一块 40×40 的 `#ff00ff`，`badPixels` 0 → **1600**；涂**调色板内**的颜色也一样算越界（见下） |
| 2 | **总墨量 TAC** | `tac` | **≤ 上限** | 真实胶印 240–300%、Hexachrome 惯例 340%；不压则暗部四版全满、叠成一坨死黑 | 见 §7.2 —— **门限有两个口径，默认 `tacLimit 2.4` 不保证这条成立** |
| 3 | **色数** | `colors` | **≤ `paletteColors`** | `colors` 是从 `codes` 折叠来的，所以这条在实现上是"同义反复"—— 它的作用是**守住定义**：一帧最多 `paletteColors` 色，谁改动了合成路径都会在这里露出来 | 定义级（`press.js:642` 自己写明"这条门禁就成了同义反复"） |
| 4 | **每版都有墨** | `plates[k].cov` | 每版 **> 0** | 某一版空 = 分色参数把它饿死了（`ucr` 太高 / 图里没这个色系），这时"N 版套印"名存实亡 | 待标定：见下方口径注 |

> ⚠ **`badPixels` 比的是 `CODE` 缓冲，不是"颜色在不在调色板里"。** 它逐像素问的是「这个像素 == `palette[CODE[j]]` 吗」——
> 所以任何 `draw()` **之后**再往画布上涂的像素都会被记成越界，哪怕涂的正是调色板里的颜色。两条实测：
> ① 四版实例上涂一块 80×40 的 **`rgb(12,13,14)`（就是 K 墨本身，调色板内）** → `badPixels` 0 → **2 870**；
> ② 再涂一块同样大小的 `#ff00ff` → **6 070**（2 870 + 3 200）。
> 想验"有没有跑出格点集"要用**集合成员**判据：把 `paletteOf` 的 3N 元组收成一个集合，逐像素查表 ——
> 套印片（`tools/press-reel.html`）的字幕带是 `draw()` 之后整格涂黑的（`solidBand`），实测 `badPixels` **≈42 000（2.0%）**
> 而**调色板外像素 = 0**。读这两个数必须先分清问的是哪一个。

**压墨的时机**：`limitTac` 在**全部 N 版都物化之后**逐格按比例压（`press.js:681-690`，调用点在 `770-773`）。
顺序反了就成了"每版各自压" —— 压第 1 版时别的版还是 0，等于 TAC 限制完全失效。
压法是**等比缩**，所以色相不动、只变浓淡。`tacLimit ≥ N` 时它直接 `return`（`press.js:683`：`if (!(lim > 0) || lim >= N) return;`），
四版给 4.0 等于没有限制（实测 `tacLimit` 0 / 4 / 6 在 `maxFrac .52` 下的 `tac` 全是 **2.6537**）。

> ⚠ **判据 4 的口径**：它是**交版时**（`plates` 这一份分色产物）的门槛，不是每一帧的门槛。
> 套印片里 `t = 7.0` 那帧肌肤题材的 **Y 版覆盖率就是 0.0%**（画面里没有黄色），片子照播 —— 视频里题材一换，某版空掉是正常的。
> 逐帧硬套这条会得到恒假门禁。另外：`ucr 1` + 纯黑源时**只有 Y 归零**，C 0.3114 / M 0.1453 仍有墨（不是旧版文档写的"C/M/Y 全为 0"）。

### 7.2 TAC 的两个口径（这一条最容易写错）

`limitTac` 压的是**每格墨量 `w` 之和**；`measure().tac` 报的是**各版覆盖率之和**。两者差一条 `coverageCurve`。
所以 **`tac ≤ tacLimit` 这条判据并不总成立**：

| `maxFrac` | `tacLimit 2.4` 时的 `tac` | 不压时（`tacLimit 0/4/6`） |
|---|---|---|
| .40 | 1.1073 | 1.1073 |
| .48 | 1.6887 | 1.6887 |
| .52 | 2.1016 | **2.6537** |
| .56 | **2.4034（已超 2.4）** | 3.0494 |
| .60 | 2.6537 | 3.2693 |
| .70 | 3.2693 | — |

（源＝满幅纯黑 `320×180` → `160×90` 格 / 四版 45° / `ucr .55`，`.visual-audit/tac3.cjs`。）
`maxFrac .56` 时 `limitTac` 认为没超、`measure()` 报 2.4034 > 2.4 —— 这是**口径差，不是 bug**。三条结论：

1. 想拿 `tac ≤ tacLimit` 当硬门禁，就把 `maxFrac` 压在 **≤ .52**（或把门限除以该 `maxFrac` 下 `maxCov` 与 1 的比）。
2. `tacLimit ≥ N` 是空操作（`lim >= N` 直接 `return`）。四版想真限墨就给 **2.4–3.0**，别给 4。
3. `press.html` 的判据 2 用的是**覆盖率门限** `COV_LIMIT = {3:3.0, 4:3.0, 6:3.4}`（300% / 340%），不是 `tacLimit` —— 那才是同口径。

### 7.3 两个体裁绑定指标：`fringe` 与 `platesPerInk`

| 指标 | 定义 | 怎么读 |
|---|---|---|
| `fringe` | 只被**一版**盖到的非黑像素 ÷ 总像素（`press.js:805`；黑版单盖算正常网点，不算漏色） | 越大 = 漏色重影越多 |
| `platesPerInk` | `tac / inkCov` = 每颗着墨像素**平均叠了几版**（`press.js:826`） | 越大 = 套得越准（各版圆盘重叠得多） |

实测（源 A；1280×720 CSS / `scale 1.5` / `cell 8` / `maxFrac .40` / `ucr .55` / `tacLimit 2.4` / `speed .8` / `seed 3` / `t=0.9` / `rot 0`）：

| 状态 | `regPx` | `fringe` | `platesPerInk` | `colors` / `codes` |
|---|---|---|---|---|
| 严格对齐 `amp 0` | 0 | **0.0623** | **2.808** | 7 / 8 |
| `amp 2` | 1.43 px | 0.1471 | 1.846 | 15 / 16 |
| `amp 4` | 2.86 px | 0.2518 | 1.350 | 13 / 13 |
| `amp 6` | 4.29 px | 0.2984 | 1.255 | 12 / 12 |
| `amp 8` | 5.72 px | 0.3194 | 1.242 | 14 / 14 |
| 玫瑰斑 · 对齐 | 0 | **0.3069** | **1.310** | 15 / 16 |
| 玫瑰斑 · `amp 5` | 3.58 px | 0.2908 | 1.333 | 15 / 16 |

`rot` 扫描（`amp 0`；`regPx` 恒 0 —— 微转不产生平移）：

| `rot` | 0.1 | 0.2 | 0.3 | 0.5 | 0.8 |
|---|---|---|---|---|---|
| `regRot` | 0.089 | 0.177 | 0.266 | 0.443 | 0.709 |
| `fringe` | 0.0596 | 0.0822 | 0.1129 | 0.1454 | 0.1765 |
| `platesPerInk` | 2.302 | 1.903 | 1.724 | 1.602 | 1.532 |

> ⚠ **这两个指标只在"同角度基准"下有意义**。玫瑰斑的 `platesPerInk` 天生就低（各版点位本来就不同），
> 拿它当"套得准不准"会得到恒假的读数：玫瑰斑对齐 `fringe` **0.3069** —— 比同角度**歪到快撕碎**（`amp 8`，0.3194）还接近。
> `fringe` 也不是一路单调：`amp` 越过约一格之后会走平甚至回落（`amp 8` 0.3194 → `amp 10` 0.2787 → `amp 12` 0.2030），
> 因为错位太大时整片都成了"多版叠印"，单版孤岛反而消失。

### 7.4 这两个指标**内容相关**，而且**随时间摆动**

同一套参数换一张源图（对齐态与 `amp 5` 各测一次）：

| 源 | 对齐 `fringe` / `platesPerInk` | `amp 5` `fringe` / `platesPerInk` |
|---|---|---|
| A · 光谱渐变 + 深盘（中调为主） | 0.0623 / 2.808 | 0.2804 / 1.282 |
| B · 浅色留白（两小块色，大片纸） | 0.0360 / 1.584 | 0.0493 / 1.118 |
| C · 深色满幅（暗调渐变） | 0.0097 / 3.561 | 0.3217 / 1.487 |

→ 对齐态差 **6.4 倍**、`amp 5` 差 **6.5 倍**。

同一帧序列里（`amp 5` + `rot .3`，走完一个 12 s 周期，13 个采样点）：
`regPx` **2.59–5.78 px** · `fringe` **0.1402–0.3834** · `platesPerInk` **1.196–1.691** · `colors` **11–15**。

> ⚠ 结论：`fringe` 与 `platesPerInk` 是**同一画面、同一参数下的纵向比较量**，不是跨画面的硬门禁。
> 别写"fringe 必须 < 0.2"这种规矩 —— 换张图它就恒假。要当门禁就用 §7.1 那四条。

## 8 · 性能边界

实测环境：headless Edge / 1280×720 CSS / `cell 8`（160×90 格）/ `maxFrac .40` / `areaMap` / `drift amp 4 rot .3`；
**每档独立建实例、串行量、20 帧预热、60 帧取中位**，只算 `draw(t)`（`.visual-audit/probe-pf4.js`）。
下表给**两轮**的区间，不是单次读数（同一台机器、同一份代码，两轮就能差 15%）：

| 背板 | 0 版 | 1 版 | 2 版 | 3 版 | 4 版 | 6 版 | 8 版 | render 对照 |
|---|---|---|---|---|---|---|---|---|
| **1920×1080**（`scale 1.5`） | 6.2–6.5 | 6.6–7.6 | 8.9–10.3 | 10.8–12.5 | **12.3–14.4**（p90 15–18） | **18.3–21.0**（p90 20–27） | 22.5–23.0 | `shutter 1/28` 20.1–20.3 / `shutter 0` 13.4 |
| **1280×720**（`scale 1`） | — | — | — | — | **7.7–7.9** | 10.3 | — | — |

- **每多一版约 +1.6–2.6 ms**（1080p，1→4 版约 +5–7 ms）。四版不是四倍 —— 每版走同一个 render 实例，`maskOnly` 直接 `OR` 进套印码（`press.js:646-656`），省掉了每版一帧的 RGBA 中转。
- **0 版也不免费**：1080p 下 `CODE.fill(0)` + `putImageData` + 整帧查表合成 ≈ **6.2–6.5 ms**。这是固定成本。
- `measure()` **另算**：整帧 `getImageData`（1080p ≈ 8.3 MB）再逐像素比对 —— 四版 1080p 实测 `draw` 12.5–13.6 / `draw + measure` 17.6–18.7 / `measure` **4.8 ms**。实时预览别每帧量。
- `toDataURL('image/png')`（1920×1080，源 A）**10.5–10.6 ms** / 输出 760 302 B。压缩率强依赖内容（早前一轮同页量到 19–25 ms），别拿它当常数。
- **分色才是多色的瓶颈**（见下表）：六色 `separateCov` 是绘制的 2–4 倍，八版更贵。

| 一次性开销（`cell 8` / 160×90 格） | 四色 | 六色 |
|---|---|---|
| `separate`（UCR 公式） | 15.0–15.3 ms | — |
| `separateN`（密度域 NNLS） | — | 48.2–54.7 ms |
| `separateCov` `sweeps 12` / `24` / `30` | — / 21.9–27.2 / — | 24.5–28.0 / **41.7–42.8** / 50.8–52.1 ms |
| `coverageCurve`（24 steps） | 18–24 ms（**必须缓存**） | 同左 |

**两条路径**：

| 路径 | 预算 | 建议 |
|---|---|---|
| **实时预览** | 每帧 ≤ 33 ms（30 fps） | `scale ≤ 1.5` · `cell ≥ 8` · **≤ 4 版**（六版要 `sweeps 12` + 分色别每帧重跑）· 每 6–10 帧量一次 `measure()` |
| **离线导出** | 0.02–0.03 s/帧（`draw` + `toDataURL`） | 可上 8 版、`scale 2`、`cell 6`；12 s × 30 fps = 360 帧 ≈ 8–15 s 出完 |

> ⚠ 上表是本机实测，量的时候机器上**有别的进程在跑** —— 同一参数在不同轮次里能差 1.9 倍
> （四版 1080p 的各轮中位见过 12.3 / 14.4 / 15.4 / 20.4 / 35.7 ms）。拿它当**数量级**，别当常数；换个负载就重量一次。

真实成片的账（`tools/press-reel.html` **母版**：1920×1080 / `cell 7` / **274×154 格** / 六色玫瑰斑 / 覆盖域 `sweeps 30`）：
`benchParts(3)` 连跑五轮，**paint 17–22 + sep 202–213 + band 4–5 + draw 32–33 ≈ 258–267 ms/帧** —— 分色占 **77–80%**。
17 s × 30 fps = 510 帧 → 实测整片 **122.8 s**（约 241 ms/帧，含 PNG 编码；编码与取帧并行，比单帧成本还低一点）。
`benchParts()` 把四个分量分开报，才知道该砍哪一段 —— 这一版要压时间只能动分色：`sweeps` 降到 12 约省 60%，
或把网格降回 183×103（格数少 2.2 倍，分色按格数线性），代价是字版版面碎掉（§10.3）。

> ⚠ 上一版这行写的是「92–133 ms/帧，分色占 70–74%」，那是 **183×103 格**的量。网格换到 274×154（格数 2.2 倍），
> 分色与栅格化都近乎线性地涨上去了 —— 同一个文件、同一台机器，只是格子多了。

## 9 · 最小用法

经典脚本，零依赖。**装载顺序 `fields.js → render.js → judge.js → host.js → dotink.js → press.js`**。
`press.js` 必须在 `render.js` 之后（圆盘栅格化在 render 里）、`dotink.js` 之后（它挂 `DotInk.press`）；
仓库的自查 `check/core.mjs` 就按这条口径查所有页面。

```html
<canvas id="cv" style="width:1280px;height:720px"></canvas>

<script src="fields.js"></script>
<script src="render.js"></script>   <!-- 几何与圆盘栅格化全在这里 -->
<script src="judge.js"></script>
<script src="host.js"></script>
<script src="dotink.js"></script>   <!-- 汇总入口，必须压在所有核件之后 -->
<script src="press.js"></script>    <!-- 必须在 render.js 与 dotink.js 之后 -->

<script>
const CW = 1280, CH = 720, CELL = 8;
const COLS = Math.round(CW / CELL), ROWS = Math.round(CH / CELL);

/* ① 一张画面：视频帧、设计稿、生成的图都行。这里画的是全文那张"源 A" */
const src = document.createElement('canvas');
src.width = CW; src.height = CH;
const sx = src.getContext('2d', { willReadFrequently: true });
const g = sx.createLinearGradient(0, 0, CW, CH);
g.addColorStop(0, 'hsl(210,72%,30%)');
g.addColorStop(1, 'hsl(70,60%,86%)');
sx.fillStyle = g; sx.fillRect(0, 0, CW, CH);
sx.fillStyle = 'rgba(12,13,14,.9)';
sx.beginPath(); sx.arc(CW * .66, CH * .40, CH * .30, 0, 7); sx.fill();

/* ② 分色：RGB → C/M/Y/K 四张版，每版每格一个墨量 0..1（纯函数） */
const rgba = sx.getImageData(0, 0, CW, CH).data;
const plates = DotInk.press.separate(rgba, CW, CH, COLS, ROWS, { ucr: .55 });

/* ③ 建实例：四版都是 45°（准同角度），靠 drift 把它们晃开 */
const inst = DotInk.press.create({
  canvas: document.getElementById('cv'),
  cssW: CW, cssH: CH,
  scale: 1.5,                       /* 实机请用 devicePixelRatio —— 这里写死只为让下面的读数可复现 */
  cell: CELL, maxFrac: .40, areaMap: true, floor: .035,
  plates: plates,
  inks: [
    { name: 'C', rgb: [0, 174, 239],  angle: 45 },
    { name: 'M', rgb: [236, 0, 140],  angle: 45 },
    { name: 'Y', rgb: [255, 241, 0],  angle: 45 },
    { name: 'K', rgb: [12, 13, 14],   angle: 45 },
  ],
  ucr: .55, tacLimit: 2.4,
  drift: { amp: 5, speed: .8, seed: 3, rot: .3 },
  duration: 12,
});

/* ④ 画一帧，量一帧：四条硬判据的原料都在 measure() 里 */
inst.draw(4.0);
const m = inst.measure();
console.log('✓ 套印 ' + m.colors + '/' + m.paletteColors + ' 色 · regPx ' + m.regPx.toFixed(2) + 'px'
  + ' · TAC ' + (m.tac * 100).toFixed(1) + '% · 漏色 ' + (m.fringe * 100).toFixed(1)
  + '% · 每版 ' + m.platesPerInk.toFixed(2) + ' 版 · 越界 ' + m.badPixels + 'px');

/* ⑤ 播放：draw(t) 是纯函数，t 只走 0..duration */
let t0 = 0;
requestAnimationFrame(function loop(now) {
  if (!t0) t0 = now;
  inst.draw(((now - t0) / 1000) % inst.duration);
  requestAnimationFrame(loop);
});
</script>
```

这一段是**真跑过**的（headless Edge、无 JS 报错、与本页所有表同一张源 A）。实测输出：

```
✓ 套印 13/15 色 · regPx 3.13px · TAC 64.7% · 漏色 23.2% · 每版 1.32 版 · 越界 0px
```

（`colors 13 ≤ paletteColors 15`、`badPixels 0`、每版 `cov` 都 > 0 —— 四条判据在这一帧全过。）

**六色要换三个地方**：墨组加 O/G、分色换成覆盖域、`tacLimit` 抬到 4.2。

```js
const P = DotInk.press;
const inks6 = P.CLASSIC.concat([
  { name: 'O', title: '橙', rgb: [255, 108, 0], angle: 30 },
  { name: 'G', title: '绿', rgb: [0, 166, 81], angle: 60 },
]);
const curve = P.coverageCurve({ cell: CELL, maxFrac: .40, scale: 1.5, canvas: document.createElement('canvas') });
const srcAvg = P.cellAverages(rgba, CW, CH, COLS, ROWS);
const plates6 = P.separateCov(inks6, rgba, CW, CH, COLS, ROWS, { curve: curve, srcAvg: srcAvg, sweeps: 24 });
/* 之后 create({ plates: plates6, inks: inks6, tacLimit: 4.2, … }) —— 其余不变 */
```

实测输出（同一帧、`amp 4 / rot .3 / t 4.0`）：

```
✓ 六色 玫瑰斑 35/35 色 · 64/64 掩码 · TAC 104.0% · 漏色 35.6% · 越界 0px
  每版 C 26.6% · M 24.7% · Y 2.8% · K 6.8% · O 9.8% · G 33.2%
```

> ⚠ `inst.opts` 是**活引用**：改 `opts.tacLimit` / `opts.drift` 立刻生效，不必重建（`press.html` 的滑杆就是这么接的）。
> 但换 `inks` **必须重建实例** —— `setInks()` 是故意抛错的（`press.js:888-889`：
> `press: 换 inks 会改调色板与缓冲名，请重建实例（new DotInk.press.create）`），因为调色板与缓冲名都跟着版名走。

> ⚠ **先 `draw` 再 `measure`**。第一帧之前画布还是空的，实测 `measure().badPixels` 会报 301 371（拿空白画布去比格点集），
> 别把它当成"画坏了"。

为什么非得是照片：这一层的立论是"颜色只在 2^N 个格点集上"，它必须落在**真实的连续调**上才成立。
手绘示意图在 183 格宽的点阵里永远是一块色（母版 274 格也一样）—— 四轮返工全败，记录留在片源页的 `_p3` 分片注释里。

低于一格的笔画在 1-bit 里**不存在**。照片反过来有毛孔、发丝、叶脉这些正好落在格子尺度上的高频细节，
于是"网点化"本身成了信息，而不是把信息抹平。

### 10.2 低通：采样定理，不是审美

源画布**按格定**（`SW = COLS·SPX`，`SPX` 默认 **6**）。母版是 `cell 7` / 1920 CSS / `scale 1` → **274×154 格**，
源画布 **1644×924**（一格 = 6 源像素），印在 **7.0 设备像素**上。网页演示（`press.html`）用 1280 CSS / `cell 9`，
那是屏幕尺寸、不是母版 —— 两种网格下字版的版面完全不同，见 §10.3。
源图里细于一格的东西（毛孔、发丝、叶脉）落进格子只有一个去处：变成"这一格该是哪个墨"的抖动 ——
相邻两格差一点点，解出来的版就换一张，**远看是噪，1:1 是彩色纸屑**。所以贴图前先糊到点距尺度：
`ctx.filter = 'blur(Npx)'`，`N` 以**源像素**为单位，默认 **4**。

母版网格（274×154 格）上重测的 `fidelity.mean`：

| `blur` | 0 | 2 | **4** | 6 |
|---|---|---|---|---|
| t 2.2（果物） | 25.05 | 24.93 | **24.98** | 25.19 |
| t 6.5（肌肤） | 27.58 | 27.54 | **27.46** | 27.50 |
| t 10.5（风景） | 26.35 | 26.10 | **26.16** | 26.34 |

→ **格均色差几乎不动**（三张样张四档之间的极差都在 0.25 以内，没有一档稳定最优）。
这条得说实话：早先那张表（24.01 → 23.36 → 22.90 → 22.90）是在**上一版 183 格几何**上测的，网格换成 274 之后不再成立，已作废。
`blur` 保留 4 的理由因此不是"误差更小"，是**网点更干净**：不糊时相邻两格会为了一点点色调差换一张版，
1:1 看是红黄绿黑的小点浮在肤色上（彩色纸屑），糊到一格尺度后才是连续的肤色网纹 —— 这一条肉眼可见，格均色差看不见它。
印厂的说法是"这个网线数印不出这种细节"，同一件事。**别把 `blur` 当精度旋钮**。

### 10.3 版式：2.69:1 的版心只能取一条带

版心是 `contentH() = SH·(1 − CAP_BAND)` = **0.66·SH**，而源画布按格定（`SW = COLS·SPX`、`SH = ROWS·SPX`），
所以版心**恒为 2.69:1**（`COLS : 0.66·ROWS`）：
导出用的就是母版这一档：**1920 CSS · `cell 7` · `scale 1` → 274×154 格**，源画布 **1644×924**、版心 **1644×610**；
网页演示 1280 CSS · `cell 9` → 142×80 格，源画布 852×480、版心 852×317。

为什么母版非要是 274 格：**字版那一页是按 274 设计格排的版面**（`U = SH/ROWS · min(1, COLS/274)`），
而 `154×(1−0.34) = 101.64` 正是它需要的 101.6 格版心 —— 只有这一档设计格与真实格严丝合缝。
早先跑 1280 CSS × `scale 1.5`（背板同样是 1920×1080，但只有 183×103 格）时，字版版面被缩到 0.67 倍，
序号与副题掉到 1.4 格字干、整页碎成网点。**背板分辨率不等于网格密度**，这两个数要分别定。
（旧版还按 `0.55·CSSW` 定源画布，1280 宽时只有 704 宽、一格 3.85 源像素 —— 26 格大字的抗锯齿边缘会占满半格，
实墨被解成半调网纹，所以改成按格定 `SW = COLS·SPX`。）
源图是 3:2，所以 `u = 1` 时只看得见源高的 **55.7%**。**不能"适配整张图"** —— 那会把 2.69:1 压成 3:2，人脸矮一截。
每张只定三件事：取多宽的带（`u`）、带中心落在哪（`cx` / `cy`）、4.25 s 里推多近（`u0 → u1`）：

| 题材 | `u0 → u1` | `cx0 → cx1` | `cy0 → cy1` |
|---|---|---|---|
| 果物 | 0.90 → 0.84 | 0.44 → 0.46 | 0.44 → 0.46 |
| 肌肤 | 1.00 → 0.93 | 0.50 → 0.51 | 0.42 → 0.40 |
| 风景 | 0.94 → 0.88 | 0.52 → 0.54 | 0.42 → 0.435 |

`u` 接近 1 时 `cx/cy` 会算出负的源坐标，必须 clamp —— 不夹住会画出纸边（一道白线，分色后成了白点）。

### 10.4 保真度：怎么知道"印得像"

`__reel.fidelity(t)` 把渲染画布**按格取平均**，与**同一格的源色平均**比（0..255 sRGB 欧氏距离，返回 `mean / p95 / bias`）。
必须比格均色而不是源像素——分色本来就是格级别的，拿源像素比会把"格内本来就有梯度"算进误差里。

| t | 题材 | `mean` | `p95` | `bias` (R,G,B) |
|---|---|---|---|---|
| 2.2 | 果物 | 24.98 | 76.45 | −2.2 / +2.9 / +3.3 |
| 6.5 | 肌肤 | 27.46 | 79.32 | +2.3 / +7.1 / +4.1 |
| 10.5 | 风景 | 26.16 | 72.87 | +5.8 / +4.4 / +2.9 |

同一批数字**两次独立跑逐位相同** —— 片源是纯函数，这也是它的验收方式。
> ⚠ **`bias` 不恒为负**（上一版是负的，这一版是正的）。三张都偏 **+2…+7** = 印出来**略亮**。
> 原因不在编码，在 `maxFrac`：母版取 0.7071（圆盘并集刚好盖满方格）时满墨覆盖率 97.6%，
> 剩下的 2.4% 是方格的四个角 —— 每格都漏一点点纸，整幅就偏亮。想更暗就把 `maxFrac` 抬到 0.80，
> 代价是点在暗部会连成一片（见 §7 的 ⚠）。**不要**拿 `bias` 去调编码参数，它跟编码无关。

**限色（`sparsify`）默认关**：每格只留最该有的 k 版（`query sparse=k`）。实测母版网格 t 6.5（肌肤）
`fidelity.mean`：`sparse 0` **27.46** / `2` **30.81** / `3` 28.58 / `4` 27.57 / `6` 27.46（色数 27 / 16 / 17 / 27 / 27）——
开得越紧误差越大（开 2 版比不开差 **+3.35**，"精度只差 0.3" 的说法不成立），画面确实更薄，所以默认 0。
`sparse 6` 与 `sparse 0` 逐位相同：六色时"每格最多留 6 版"等于不限制。
**它和 TAC 不是一回事**：TAC 是等比缩放（色调发白），限色是**选择**（留最该有的那几版）。

### 10.5 编码：为什么网页版是 `yuv444p`，以及为什么是 1280 不是 960

套印层的现象是**网点边缘一两像素宽的漏色**，而 `yuv420p` 按 2×2 下采样色度 —— 那一圈彩边正好被抹掉。
所以网页版一律 `yuv444p`，母版走 `libx264rgb`（`gbrp`，RGB 直编、无色度变换）。

**判据要用「格均色差」，不是「逐像素相同」。** 逐像素比只答「这个像素还原得准不准」，
而这一层的颜色是**格**的性质（一格一个墨量、一格一个颜色）；网点边缘的抗锯齿像素本来就该在两色之间。
实测同一帧（母版 t=13.0，`__reel.frame(13)` 直出的 PNG 当基准；母版取第 390 帧 = t=13.0）：

| 编码 | 逐像素逐字节相同 | 格均色差 `mean` | `p95` | 体积（全片） |
|---|---|---|---|---|
| 母版 `libx264rgb` / `qp18` / 1920 | **78.0%** | **0.10** | 0.47 | 221.15 MB |
| 网页 `yuv444p` / `crf33` / 1280 | 2.2% | **3.10** | 11.71 | **7.53 MB** |
| 同尺寸 `yuv420p` / `crf36` / 1280 | 1.9% | 4.29 | 17.35 | 3.34 MB |
| `yuv444p` / `crf33` / 960 | 2.3% | 4.17 | 12.19 | 3.79 MB |

读法：**母版比网页版准 31 倍（0.10 对 3.10）**，而逐像素只差 78% 对 2.2% —— 同一件事的两个量纲。
`420` 与 `444` 在格均上只差 1.19（4.29 对 3.10），但 `p95` 差 5.6（17.35 对 11.71）：
**误差集中在网点边缘那一圈，正是本层要展示的东西**。960 与 1280 在格均上几乎打平（4.17 对 3.10），
所以取 1280 —— 同样约 4 MB 档位，先保像素密度。

`qp0` 是无损：解码回来与 PNG 静帧**逐字节相同**（上一轮已验过）。
**为什么不直接按 1280 出图、而要「1920 母版下采样」。** 试过了，两个理由都实测过：

| 方案 | 与母版格均色差 | 全片体积（yuv444p） |
|---|---|---|
| 1920 母版 → lanczos 下采样 1280（现用） | 基准 | **7.53 MB**（crf33） |
| 直接按 1280 CSS / cell 4.6715 出图（274×154 格不变） | **10.41**（p95 53.4） | 16.09 MB（crf33）/ 6.94 MB（crf42） |

直接按 1280 出图**不是同一张画**：点距从 7.0 设备像素掉到 4.67，圆盘半径按比例缩，
而字形栅格化是按设备像素做的 —— 4.67 px 的点阵里每个字的抗锯齿边缘占比反而变大，
分色解得的面场跟着变（同帧 colors 27 → 33，fringe 3.0% → 7.7%）。
体积上也不占优：要压到同样的「点还圆不圆」水平，crf 得降到 33 以上，反而比下采样版本大一倍。
**母版下采样 = 拿 2.25 倍采样点先算准，再降一次分辨率；直接小尺寸出图 = 一开始就在小网格上近似。**
所以网页版固定是「母版 → scale=1280:720:flags=lanczos → yuv444p」，出片脚本不做第二套几何。


| 用途 | 参数 | 体积 | 落点 |
|---|---|---|---|
| 网页内播放 | 1280×720 · `yuv444p` · crf 33 · 2.60 Mbps | **7.53 MB**（510 帧） | [`media/press-reel-clip.mp4`](../media/press-reel-clip.mp4) |
| poster | t=8.4 s 帧 · 1280 宽 · 48 色量化 | 271 362 B | [`media/press-reel-poster.png`](../media/press-reel-poster.png) |
| 母版（六色照片版） | 1920×1080 · `libx264rgb`（`gbrp`）· qp 18（脚本默认）· 109 Mbps | **221.15 MB**（510 帧） | `media/_release/press-reel-hex.mp4`，Release 附件（仓内不放） |
| 四张样张静帧 | 1200 宽 · 48 色量化 | 334 / 270 / 329 / 163 KB | [`media/press-specimen-01..04.png`](../media) |

> ⚠ **`yuv420p` 的体积优势没有意义**：3.34 MB 对 7.53 MB 省一半，代价是把本层的现象（边缘漏色）糊掉。
> 这一层要是为了体积牺牲漏色，那这条片子就不必存在 —— 它不是"一段好看的动画"，是一个论据。
### 10.6 `__reel` 的调试接口

片源页暴露 `window.__reel`，导出用的与调试用的分开：

| 成员 | 作用 |
|---|---|
| `ready`（getter） | 三张照片**与**素材段都 decode 完才为 `true`（`PHOTO_OK >= PHOTO_N && CLIP_OK >= CLIP_N`；§11.3） |
| `photos()` | `{ n, ok, fail }` —— 缺图会在这里露出来，不会静默出白片 |
| `clips()` | `{ n, ok, fail, list }` —— 素材段状态；缺 sidecar / 图 404 在这里露出来（§11.3） |
| `frame(t)` | 跑一帧，返回 PNG dataURL（导出走这条） |
| **`src(t)`** | 返回**分色前**的源画布 PNG —— "取景错"与"分色错"必须分开看 |
| `measure()` | `colors / paletteColors / tac / fringe / regPx / regRot / perInk / bad / amp / scene / plates` |
| `fidelity(t)` | `{ mean, p95, bias }`（§10.4） |
| `benchParts(n)` | `{ paint, sep, band, draw, total }` —— 决定要不要降 `sweeps` / 降 `cell` |
| `dur / fps / w / h / cols / rows / inks / sep / angles / mode / scenes / curve` | 当前配置 |

**两个已经修掉的坑（都跟这个接口的形状有关，重写这一页时会再踩）：**

| 症状 | 真因 | 现在怎么写 |
|---|---|---|
| `measure()` 在第一帧之前抛 `TypeError: Cannot read properties of null (reading 'amp')` | `lastMeta` 初值是 `null`，但 `measure()` 无条件读 `lastMeta.amp` | `var lastMeta = stateAt(0);` —— 初值给一个**真的状态**，不是 `null` |
| 三张图 `onload` 各抛一次 `TypeError: Cannot set property ready of #<Object> which has only a getter` | `ready` 改成 getter 之后，原来的 `syncReady(){ __reel.ready = … }` 还在给它赋值 | `ready` 由 `PHOTO_OK >= PHOTO_N` 现算，`syncReady()` 留成空函数（计数器即状态） |

> 教训是同一条：**把"状态"做成派生值，别做成要人推的缓存。** 两处都是缓存与真相脱了钩 ——
> 一处是"还没画就有读数"，一处是"还有人在写只读属性"。前者会让抽检脚本读到幻觉，后者在 `'use strict'` 下直接抛。

## 11 · 管线化：任意素材进，套印片出

§10 那条 17 秒片是**四段写死的样张**：果物、肌肤、风景、字版，顺序、时长、曲线全在片源页里。
这一节是它的反面 —— **给什么视频就印什么**：题材、时长、段数、偏差峰值都由参数决定，片源页只认一张**格子图集**。
两个工具：[`tools/press-clip.mjs`](../tools/press-clip.mjs)（视频 → 图集）与 `press-reel.mjs --clips`（图集 → 套印片）。
演示在 [`press.html`](../press.html) 的「管线」一节；素材许可归 [`NOTICE.md`](../NOTICE.md) §7.1。

### 11.1 为什么中间要多一张图集

分色是按**格**工作的（§5）：一格取一个平均色，再决定这一格上哪几版、每版多厚。
如果每次都从视频解码，同一格的平均值会随解码器、随缩放算法漂 —— **同一个 `t` 就不再出同一帧**，
而"同参数同帧"是这一层能出视频、能随机 seek 的前提（§6）。
压成图集之后，**一格 = 一个像素**，取平均这件事被提前做掉、并且**只做一次**；往下的每一帧仍然只是 `t` 的纯函数。

掉到格分辨率是**零损失**（分色只吃格均值），换来两个数量级的内存：
128 帧 × 274×102 × 4 B ≈ **14 MB**，同样 128 帧的 1080p RGBA 是 **1.06 GB**。

| 步骤 | 工具 | 输入 → 输出 |
|---|---|---|
| ① 视频 → 格子图集 | `node tools/press-clip.mjs` | `.mp4` → `<name>.png` + 同名 `.json` sidecar |
| ② 图集 → 套印片 | `node tools/press-reel.mjs --clips "…"` | 一张或多张 `.png` → `.mp4` |

> ⚠ 这一步不是"预处理"，是**判据的一部分**：图集本身可复算（同一视频同一参数 → 同一张 PNG），
> 所以"这条片子怎么来的"有物证，不靠"我当时那么设的"。

### 11.2 图集的口径

一格 = **一帧缩到网格粒度**之后的那张图。母版是 274×154 格、`SPX 6`（一格 = 6 源像素），
所以一格取 **274×102** —— 274 是格宽，102 是**版心**高（`contentH()`，§10.3）。`cols = ceil(√N)`，按**格数**取方，不是按像素取方。

| 帧数 N | `cols × rows` | 图集像素 | 备注 |
|---|---|---|---|
| 90（3 s @30） | **10 × 9** | 2740 × 918 | 管线示例每段都是这一档 |
| 128（4.2667 s @30） | **12 × 11** | 3288 × 1122 | 最后 4 格是空位（纸色） |
| 上限 | — | 8000 px 见方 | 超了直接报错，**不缩格** |

实测：128 帧那张 PNG **1 180 277 B**、`press-clip` 耗时 **395–620 ms**（三次中位 431 ms）；
90 帧的三张分别 **3 602 921 / 2 550 456 / 3 169 433 B** —— PNG 体积跟画面内容强相关，别拿它当进度条。

sidecar 是契约的一部分（片源页按它算时间轴），字段固定：

| 字段 | 含义 |
|---|---|
| `tileW` / `tileH` | 一格（= 一帧）的像素尺寸，274 / 102 |
| `n` | 帧数，`Math.round(dur × fps)` |
| `cols` / `rows` | 排布，**行优先**：第 k 帧在 `(k % cols, ⌊k / cols⌋)` |
| `fps` / `dur` / `start` | 取帧口径 |
| `src` / `srcW` / `srcH` | 源视频的绝对路径与尺寸 —— **只作溯源**，不参与渲染 |
| `fit` / `cx` / `cy` | `cover`（裁满）或 `contain`（补纸色边），与中心点 |
| `paper` | 补边与空格的纸色 `[242,243,242]` |
| `padded` | **只有真补过帧才出现**，值 = N − 真实帧数 |

> ⚠ 空格与空尾格是**纸色**，不是黑（`tile=…:color=0xF2F3F2`）。这一点在下面第一条坑里会咬人。

### 11.3 四个会静默出错的坑（这一段就是这两个工具存在的理由）

每一条都是 `exit 0` 但画面坏了 —— 所以它们是**判据**，不是建议。

| # | 症状 | 真因 | 现在怎么写 |
|---|---|---|---|
| ① | 图集里冒出一片空格子，片子后段"卡住"不动 | `tile` 在帧数不足时**用 `:color` 静默补满并退出 0**。实测 10 帧喂进 `tile=4x4` → 输出 4×4、后 6 格整格纸色（每格 1536/1536 像素 = 242,243,242）；128 帧进 12×11 = 132 格，第 128–131 格各 27 948/27 948 全是纸色 | 「恰好 N 帧」只能**自己数**：两路**命名实例** `showinfo@real`（tpad 之前）/ `showinfo@total`（之后），逐行数 `n:`，对不上就 die |
| ② | 同一段素材换个写法，格均色就漂一点 | `format=rgb24` 放在 `scale` **之后**时，ffmpeg 在解码器原生格式（yuv420p，色度已经半分辨率）上做面积平均再转 RGB —— 算的不是引擎在 sRGB 8bit 上算的那个平均值 | `format=rgb24` 必须在 `scale` **之前**（实测见下表） |
| ③ | 图集少一帧（或报"时长不够"但其实够） | `fps` 滤镜按"落在窗口内"取帧，边界那一帧给不给是浮点说了算 | `-t (DUR + 1.5/fps)` 给 headroom，再用 `trim=end_frame=N` 切掉多的 |
| ④ | 导出后半段全是重复的末帧 | 用命令行默认的 17 s 去截一条 12 s 的片 | 帧数取**页面报的**片长：`Math.round(Number(meta.dur) * FPS)` |

**②的实测**（同一源、同一参数，只改 `format` 的位置；量的是**亮度** `0.2126R + 0.7152G + 0.0722B`，因为这一层最终只看明暗）：

所以这条按**未复现**记账：保持现状即可（不影响结果），但别把它写成实测到的事实。

### 11.4 时间轴：`TS = DUR / 17`

片源那三条曲线（`driftAt` / `PLATE_IN` / `PLATE_OUT`）原本是**按秒写死**的 17 s 分镜。现在全部乘 `TS = DUR / 17`：
`TS === 1` 时 `0.5 / 12 / 0.2 / 1.3` 与 `0.42…1.14` / `16.06…16.62` 全部 **`Object.is` 逐位相等**，
所以默认那条片**一个像素都没变**（5 帧 SHA-256 两轮相等，§10.6）。

两条硬约束（都会静默错 1e-15，然后整片挪位）：

- **不能把 `TS` 折进常量**：默认路径上的数必须是 `0.5 * TS` 算出来的那一个，不是 `0.5 * DUR / 17` 重算的。
- **`fall` 不能反算**：`(14.00 − 12.70) === 1.3000000000000007`，不是 `1.3`（差 7e-16）。反算之后 `TS === 1` 就不再逐位相等，默认那条片也就不是"一个像素都没变"了 —— 这条是浮点前提，不是洁癖。

**素材模式另加一条**：回落段**锚在字版起点**上，不是锚在秒数上 ——

```
tType = DUR − TYPE_DUR
rise  = max(0.2, tType − 0.2 − a)        /* a = 0.5·TS */
fall  = min(1.3·TS, TYPE_DUR × 0.55)
```

理由是给了素材之后字版起点会变：按固定秒数回落会让长片先归位、后面一路干净地等 ——
**最该被看见的那一秒半落在没人注意的地方**。

| 片长 | `TS` | 峰值 t | 归零 t | 备注 |
|---|---|---|---|---|
| 17.00 s（默认） | 1 | 12.50 | 14.00 | 与改造前逐位相同 |
| 15.75 s（3 × 4.25 + 3 s 字版） | 0.9265 | 12.55 | 13.754 | 实测 t 12.4 峰值 7.996 px（amp 8）、t 13.4 剩 3.380、t 14.2 已 0 |
| 12.00 s（3 × 3 + 3 s 字版） | 0.7059 | 8.80 | 9.718 | 实测 t 9.96 时 `regPx` 已 0.00 |

### 11.5 实例：三段素材 → 12.00 s / 360 帧

多段用 `|` 分隔，每段自带秒数；**单条可以只给路径**，标签由文件名推出来（`parseClips` 判第一段像不像路径）。
末尾自动补一张字版（`--type`，默认 3 s），总片长 = 素材段之和 + 字版。

> **每段秒数可以省略，但省略不是"跟着图集走"** —— 没给秒数的段一律按 **4.25 s** 算（原分镜一段的长度）。
> 槽位比图集长就是**慢放**，短就是快放：取帧按**进度**映射，`k = min(n−1, ⌊p·n⌋)`，近邻取帧、不插值（`press-reel.html:376`）。
> 所以 90 帧（原 3 s）放进 4.25 s 的槽位 ≈ **0.71 倍速**，每一帧大约被停 **1.4 帧**；反过来给 3 s 的图集 1.5 s 就是 2 倍速。
> 实测（单段不给秒数、`--type 2`）：成片 **188 帧 = 6.27 s**（4.25 + 2），抽 t = 2.0 / 3.2 / 3.9 / 4.2 s 四帧 **md5 全不同** ——
> 对应的源帧分别是 k ≈ 42 / 67 / 82 / 88，说明**不是**拿末帧冻住。要精确对时就写全 `~秒数`。

> 下文那三个 `.visual-audit/pipe/*-band.mp4` 是**示例素材**（§10.1 那三张 CC0 照片各做的一段 3 s 缓推镜头），
> 生成命令（`zoompan` 那一行）在 [`press.html`](../press.html) 的管线节第 ① 步；那一步**不是管线的一部分** ——
> 第 ② 步吃的是**任何** mp4。这些路径都在点开头的目录里，不进仓、也不参与链接检查。

```bash
# ① 视频 → 图集（每段 3 s = 90 帧 → 10×9）
node tools/press-clip.mjs --in .visual-audit/pipe/fruit-band.mp4 \
     --out .visual-audit/pipe/fruit.png --cells 274x102 --fps 30 --dur 3

# ② 图集 → 套印片。多段必须用 | 分隔；拼成变量，别写成超长单行
```

## 12 · 反面清单（这些不是"风格"，是画坏了）

| 症状 | 成因 | 修法 |
|---|---|---|
| **彩纸屑**：满屏彩色小点，图像内容被吃掉 | 玫瑰斑（异角度）+ 覆盖率偏高 → 每格都错开成三四个颜色；或六色用准同角度还错位（`fringe` 0.4536） | 四色换回准同角度；六色**改玫瑰斑**；或把 `cell` 加大、`maxFrac` 降下来 |
| **满屏斜纹**：整片变成斜向条带，看不出画面 | `regPx` 超过约 **1 个格**（`amp ≳ cell`）→ 四版圆盘不再重叠，相邻格的相位差连成条纹 | 位移收到 **2–7 px**（`cell 8` 时 ≈ 0.25–0.9 格）；要更狠的效果就同时加大 `cell` |
| **暗部糊死**：深色区变成一块死黑，套印感全没了 | `ucr 0`（四色硬扛）+ 暗部 + 三版全满 → 三版圆点几乎完全重合，叠出来是一块实心；`tacLimit` 给 4 时压墨根本不生效 | `ucr` 回 **0.55**（暗部留一点给黑版）；`tacLimit` 给 **2.4–3.0**（≥ N 是空操作） |
| **点挤成噪点**：结构读不出来，像砂纸 | `cell 4–6` + 四版：设备像素下每格只剩 6–9 px，四个圆点挤在一格里（`cell 4` 的 `fringe` 比 `cell 8` 高 10%+） | `cell ≥ 8`（1080p 背板下 `cell 8` = 12 设备像素）；要细就加 `scale`，别缩 `cell` |
| **完全没偏移**：`fringe` 恒定、四版像一张版 | 自己包了一层 `rnd`（或从全局借 `_mulberry32` 并给了常数兜底）→ 四版同相位、整组平移 | 直接用 `DotInk.press.regOf`；它自带私有 `mulberry32`，不依赖装载顺序 |
| **偏移不生效**：改了 `opts.drift` 还是不动 | 改的是副本而不是 `opts` 本身；或 `drift` 传了 `null` 之后忘了写回 | 直接 `inst.opts.drift = {...}`；换 `inks` 就新建实例 |
| **六色发白**：整体像被冲淡 | 六版还用 `tacLimit 2.4`（平均每版只许 0.4），覆盖域解出来的墨被等比砍掉一大截 | 六色用 **4.2**（`press.html` 的 `TAC_BY_PLATES`）；判据 2 换成覆盖率口径 340% |
| **等距横线/竖线**（白线或黑线） | 源画布与网格 1:1 时的 `Math.floor` 映射瑕疵（§14.1）—— `separate` 出白线、`separateCov` 出黑线 | 让源画布**大于**网格（靠平均降采样）；换 `separateCov` **不能**解决 |

## 14 · 两个已知的实现瑕疵（会咬人，先记在这）

### 14.1 源尺寸与网格 1:1 时 `Math.floor` 会吞行/列（两条分色路径都踩，症状相反）

`separate()`（`press.js:167`）与 `cellAverages()`（`press.js:352`）把源图映射到网格时用的是同一个式子：
`Math.min(rows - 1, Math.floor(y / h * rows))`。当**源尺寸恰好等于网格尺寸**，`y / h * rows` 在少数行上算出 `k − ε`，
floor 成 `k − 1` —— 那一行**并进了上一行**，而 `k` 这一行一个样本都收不到。

| 源 → 网格 | 收不到样本的单元 | 形态 |
|---|---|---|
| 1280×720 → 160×90（8×） | 0 / 14 400 | — |
| 320×180 → 160×90（2×） | 0 / 14 400 | — |
| 106×60 → 106×60（1:1） | **0** / 6 360 | — |
| **160×90 → 160×90**（1:1） | **800 / 14 400（5.56%）** | 5 整行：13, 26, 49, 52, 63 |
| **213×120 → 213×120**（1:1） | **960 / 25 560（3.76%）** | 8 整列：31, 57, 62, 109, 114, 119, 124, 127 |
| **183×103 → 183×103**（1:1） | **1 680 / 18 849（8.91%）** | 6 整行（2, 4, 8, 16, 32, 64）+ 6 整列（15, 30, 51, 60, 103, 121） |

**两条分色路径都会踩，而且症状相反** —— 这是最容易看漏的一处：

| 路径 | 空格子的 `cnt` | 解出来的墨 | 画面上是 |
|---|---|---|---|
| `separate()`（UCR 公式） | 0 | 0（`cnt[j] > 1` 才除，初值原样留着） | **横向白线**：一行一个墨点都不落 |
| `separateCov()`（覆盖域） | 0 → `cellAverages` 里除的是 `cnt[j] \|\| 1` | `0 / 1 = 0` = **纯黑目标** → 解成四版全满 | **横向黑线**：比周围重得多 |

实测（`160×90 → 160×90`、源为纯中灰 `#808080`、逐行平均亮度 0..255）：

| | 正常行 | 掉的那 5 行 |
|---|---|---|
| `separate` 路径 | 210.6 | **229.3 / 229.3 / 237.4 / 218.6 / 242.7**（更**白**） |
| `separateCov` 路径 | 138.6 | **96.0 / 95.5 / 111.4 / 109.2 / 109.4**（更**黑**） |
| 该行格心的四版墨量和 | 1.226 | `separate` **0** · `separateCov` **4.0** |

> ⚠ 所以「换 `separateCov` 就安全了」是**错的**。它不修这一条，只是把白线换成黑线 ——
> 黑线还更容易被当成"画面本来就这样"放过去。

- **触发条件**：源画布与网格**同尺寸**。踩不踩是浮点运气，不是"行列数好不好"：106×60 干净，183×103 踩掉 8.91%。
- **四条硬判据都抓不到它**：不越界（颜色仍在格点集里）、不超 TAC、色数正常、每版也都还有墨。
- **绕法**：让源画布**大于**网格，靠平均降采样 —— `press.html` 是 `360×202 → 160×90`，套印片母版是 `1644×924 → 274×154`（每格 6 源像素），实测都是 **0**。
- 这一条**没有改** `press.js`（记账在此）。自查里也没有对应测试 —— 因为它不在四条判据之内。

## 15 · 边界

- **只管成像，不管印刷**：本页说的 TAC / UCR / 网角都是**成像参数**，不是分色标准（没有 ICC、没有网点扩大曲线、没有纸白补偿）。
- **没有 CMYK→sRGB 的色域映射**：`inks` 里给的就是"满版印在这张纸上的 sRGB 值"，换纸就换 `paper`、换油墨就换 `rgb`。它不保证与任何一台真实印刷机对齐。
- **不做叠印率（trapping）与套印顺序**：减色乘法是**可交换**的，所以 `inks` 的顺序只影响位序与调色板下标，不影响颜色。
- **不做纸张纹理、油墨渗边、干退**：本层只有"圆点 + 位移"，没有材质。
- **`separateCov` 不是解析精确解**：异角度（玫瑰斑）下"各版独立盖住 c 面积"是精确模型；同角度时真实分区是**嵌套环**，独立模型是近似（引擎报的 `c_i` 里已含并集压缩）。要做解析版得每格枚举墨序。
- **性能数字绑死本机**：不同机器 / 不同浏览器 / 有没有别的进程在跑，能差 1.9 倍以上。§8 是数量级，不是常数。
- **成片的套印曲线不是本层的规范**：它按 `TS = DUR/17` 缩放、素材模式下锚在字版起点（§11.4），属于那两条片子，不是判据。
